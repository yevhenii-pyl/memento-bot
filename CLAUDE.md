# CLAUDE.md — Memento bot conventions

This file is the authoritative reference for how code in this repo is structured.
Follow these rules in every PR. Deviations require an explicit ADR.

## Module structure

The bot package is split into feature modules. Each feature lives entirely in
`bot/<feature>/` and contains four files at most:

| File | Purpose |
|---|---|
| `handler.py` | aiogram Router — receives Telegram updates, calls service |
| `service.py` | Business logic — orchestrates repo calls, raises domain exceptions |
| `repo.py` | All SQL — receives an `AsyncSession`, returns domain objects |
| `models.py` | SQLAlchemy ORM models for this feature |

Shared infrastructure lives in `bot/shared/`.

## Router registration pattern

Each feature's `handler.py` exposes a module-level `router = Router()`.
`bot/main.py` includes all feature routers into the top-level Dispatcher:

```python
from bot.tasks import handler as tasks_handler
dp.include_router(tasks_handler.router)
```

No other file includes routers.

## DB session access via middleware

Handlers and services receive an `AsyncSession` injected by `DbSessionMiddleware`
(defined in `bot/shared/db.py`). They **never** call `async_session_factory` directly.

```python
# handler.py
async def handle_foo(message: Message, session: AsyncSession) -> None:
    result = await task_service.do_thing(session, message.from_user.id)
```

## Repository pattern

All SQL lives in `<feature>/repo.py`. Services call repo functions; they never
import SQLAlchemy constructs directly.

```python
# service.py calls repo, not SQLAlchemy
tasks = await task_repo.get_pending(session, worker_id=user.id)
```

## Error handling

Services raise domain exceptions from `bot/shared/exceptions.py`.
Handlers catch them and send user-facing replies. No bare `except Exception`
is allowed outside `bot/main.py`.

## ID strategy

All primary keys are `UUID` generated by `uuid.uuid4()`, stored as PostgreSQL
`UUID` column type via SQLAlchemy `Uuid` or `UUID(as_uuid=True)`.

## Migration workflow

1. Add or modify ORM models in `<feature>/models.py`.
2. Import the model in `migrations/env.py` (see the comment block there).
3. `alembic revision --autogenerate -m "short_description"` — review the generated file.
4. `alembic upgrade head` — apply.

File naming convention: `NNNN_short_description.py` (e.g. `0002_add_tasks_table.py`).

## Test layout

```
tests/
  unit/<feature>/          # Service tests — repos mocked with AsyncMock
  integration/<feature>/   # DB tests — use the async_session fixture from conftest.py
```

Unit tests must not hit the database. Integration tests run against a real schema
created by `alembic upgrade head` in `tests/integration/conftest.py`.

## Inter-module import rules

- `notifications` may import from `tasks` and `users`.
- No other cross-module imports are allowed.
- No feature module imports from another feature's handler or service.

## Claude API call convention

All calls to the Anthropic API go through `bot/shared/claude_client.py`.
Feature modules never import `anthropic` directly.

```python
from bot.shared.claude_client import parse_deadline

deadline_iso = await parse_deadline(raw_text)
```

## Scheduler jobs

All APScheduler job functions live in `bot/notifications/jobs.py`.
They receive a `bot` instance injected at schedule time; they never read from
global state.

## Running locally

```bash
cp .env.example .env          # fill in BOT_TOKEN, DATABASE_URL, ANTHROPIC_API_KEY
pip install -e .[dev]
alembic upgrade head
python -m bot.main
```

Or with Docker Compose:

```bash
docker compose up             # starts bot + PostgreSQL
docker compose run bot alembic upgrade head
```
